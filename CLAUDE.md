# KMPlus Nexus

Enterprise integration platform (EiPaaS): connect, transform, govern, and distribute enterprise data (HR-first) for KMPlus products (KMS, LMS, TMS, PMS, CMS, IMS) and third-party systems.

**Read [docs/PRD.md](docs/PRD.md) before building a feature.** It defines the product, the glossary (§5), the requirements per layer with IDs (§7), what's real and what's still mock (§10), the target architecture (§11), and the build rules (§14). When a feature moves from mock to real, update the §10 status table in the same change.

## Stack
Next.js 16 (App Router) · React 19 · TypeScript · Tailwind v4 + shadcn/ui · Better Auth · Drizzle ORM on Supabase Postgres (project `kissurqzqwvkvwcyfbhc`, Tokyo, via the transaction pooler) · deployed on Vercel (push to `main` auto-deploys).

## Commands
```bash
pnpm install          # pnpm only, never npm/yarn
pnpm dev
pnpm build
vercel env pull .env.local --environment=development --scope irfanalfieris-projects --project kmplus-nexus-platform
node --env-file=.env.local scripts/db-migrate.mjs           # list pending drizzle/*.sql migrations
node --env-file=.env.local scripts/db-migrate.mjs --apply   # apply them (tracked in public.nexus_migrations)
node --env-file=.env.local --experimental-strip-types scripts/db-repair-schema.mjs   # drift check: live DB vs lib/db/schema.ts
node scripts/run-ts.mjs scripts/engine-tests.ts                                       # pipeline engine/transform/watermark tests (no DB)
node --env-file=.env.local scripts/run-ts.mjs scripts/connector-harness.ts            # test → scan → sample for every connector
node --env-file=.env.local scripts/run-ts.mjs --stubs scripts/integration-tests.ts    # server actions, permissions, worker (nexus_dev/nexus_test only)
node --env-file=.env.local --experimental-strip-types scripts/reencrypt-credentials.mjs [--apply]   # after an encryption key rotation
node --env-file=.env.local scripts/reset-2fa.mjs --email <address> [--apply]           # break-glass 2FA reset (no admin left to do it in Settings)
node scripts/generate-test-data.mjs                                                   # fictional HR test files in test-data/ (scenarios + expected results in test-data/README.md)
node scripts/run-ts.mjs scripts/mock-kmplus.ts [port] [token]                         # local KMPlus product (Ingest Contract) on :4010; needs NEXUS_ALLOW_PRIVATE_URLS=true
node scripts/webhook-receiver.mjs <signing-secret> [port]                             # local outbound-webhook receiver on :4020 that verifies signatures
```
**Databases:** Production uses the `postgres` database; Preview and Development (and therefore `.env.local`) use the separate `nexus_dev` database on the same Supabase server, with their own `NEXUS_ENCRYPTION_KEY`. To migrate production, run `db-migrate` with `DATABASE_URL` set to the production URL (same as dev with `/postgres` instead of `/nexus_dev`). Production `DATABASE_URL` is a sensitive Vercel variable and can't be pulled. Dev and preview have no scheduler.

**Checks before pushing:** `pnpm typecheck`, `pnpm test:engine`, `pnpm test:integration`, `pnpm build` (CI runs the same on every push and PR; integration tests run against a Postgres service container).

## Rules
- **pnpm only.** After any dependency change, commit `pnpm-lock.yaml`. Vercel installs with `--frozen-lockfile`, so a stale lockfile fails the deploy.
- **Schema changes:** edit `lib/db/schema.ts`, run `DATABASE_URL=postgres://unused npx drizzle-kit generate --name <change>` (or `--custom` for hand-written SQL), commit the SQL in `drizzle/`, then apply with `scripts/db-migrate.mjs --apply`. Never apply migrations by hand, or the tracking table falls out of sync. **Never edit a migration that has been applied**: `db-migrate` stores a checksum and refuses to run if an applied file changed; put the change in a new migration. Every new table needs `ALTER TABLE ... ENABLE ROW LEVEL SECURITY` (see `drizzle/0001_enable_rls.sql`): Supabase exposes `public` through its REST API, and RLS without policies blocks that while the app (connecting as `postgres`) is unaffected. Column names are camelCase and must be quoted in raw SQL (`"userId"`). Unquoted SQL creates lowercase columns and breaks Drizzle queries.
- **Server actions return errors as values.** Next.js production hides the message of any error thrown from a server action, so every exported action in `app/actions/*` is a thin wrapper `export async function x(...args) { return guard(() => xImpl(...args)) }` (`lib/server-action.ts`) around a throwing `xImpl`. **Client components (and server pages) import actions from `@/lib/actions/<file>`**, which throws the error again with its real message; never import `@/app/actions/*` from UI code. Server code that needs another action's logic calls a helper in `lib/` (e.g. `lib/connectors/install-check.ts`), not the exported wrapper. New action: write `async function fooImpl`, add the wrapper at the bottom, add `foo` to `lib/actions/<file>.ts`.
- **Workspaces & permissions:** all shared data belongs to a workspace (`workspaceId` column); `userId` only records who created or acted. Every server action starts with `const ctx = await requireWorkspace('<permission>')` (or no argument for read-only), validates every argument with zod, **scopes every query by `ctx.workspaceId`**, records mutations and views of real data with `recordAudit(ctx, { action, resource, resourceId, changes, diff })` from `lib/audit.ts` (adds IP + user agent; never put secret values in `changes`; for updates pass `diff: diffObjects(before, after)` from `lib/audit-diff.ts`, which records secrets only as "changed"), then `revalidatePath('/dashboard')`. Permissions and roles live in `lib/auth/permissions.ts` (client-safe); the UI hides controls with `useCan(permission)` from `components/workspace/workspace-context.tsx`, but the server check is the real one. Create ids with `newId('prefix')` (UUID), never `Date.now()`. New tables holding workspace data need `workspaceId` + an index. Dataset physical tables are named per workspace; existing ones keep their stored `tableName`.
- **Credentials:** `data_sources.credentials` is encrypted with AES-256-GCM via `lib/security/credentials.ts` (`encryptCredentials(id, obj, workspaceId)` on write, `decryptCredentials(id, stored)` on read). Envelopes are v2: sealed with a per-workspace key derived (HKDF) from the master key and bound to the source and workspace; v1 rows still decrypt and upgrade on re-save or `reencrypt-credentials`. File Upload sources hold only a server-assigned `storageKey` (never accept one from the browser). Never return credentials to the client, never log them. Requires `NEXUS_ENCRYPTION_KEY` (32 bytes, base64). Envelopes carry a key id; to rotate, set the new key, move the old one to `NEXUS_ENCRYPTION_KEY_PREVIOUS`, deploy, run `scripts/reencrypt-credentials.mjs --apply`, then drop the old key. Custom credential forms (REST, Salesforce) are edited with secrets masked as `KEEP` (`lib/connectors/secret-mask.ts`); add new secret fields there.
- **Governance:** dataset policies (`dataset_policies`, `lib/governance/*`) classify and mask columns and hold **row-level filters per role** (`lib/governance/row-filters.ts`). Any code that returns dataset rows must use `accessFor(workspaceId, dataset, role)` (masks + row filters) with `applyMasks` and pass `rowFilters` to `readDatasetSample` / SQL builders; live source rows use `liveTableAccess`. Roles with `data:unmasked` (admin, steward) see real values. Analytics passes masked columns as `blockedColumns` and `rowFilters`. Datasets have system columns `_nexus_id`, `_nexus_loaded_at`, `_nexus_run_id`, `_nexus_deleted_at`, `_nexus_chunk`: every read excludes soft-deleted rows and never returns system columns. Appends pass `runId` + `chunk` to `writeDataset` so a resumed chunk replaces its earlier copy (exactly-once). Retention runs hourly from the cron tick.
- **Analytics:** widget specs are `lib/analytics/definition.ts` (client-safe); `buildWidgetSql` (`lib/analytics/query.ts`, pure, tested) only accepts dataset column names and binds every value. Queries run read-only with a 15 s statement timeout. Charts follow the data-viz rules in `components/analytics/charts.tsx` (slot-1 blue, table view for every chart).
- **Data API** (`/api/v1/*`, `lib/api/*`): Bearer keys `nxk_…` (only a SHA-256 hash stored, `lib/api/keys.ts`), scopes `datasets:read` / `domains:read` / `pipelines:run` / `runs:read`, read as the key's role (masks + row filters). Every route goes through `handle()` in `lib/api/serve.ts` (auth, per-key rate limit with X-RateLimit headers, JSON errors). Query parsing and SQL are pure (`lib/api/query.ts`, tested); every read is audited as `API_READ`. Never expose a dataset column that isn't in its column list. Update `lib/api/openapi.ts` (served at `/api/v1/openapi.json`) with every endpoint change. Outbound webhooks: `emitEvent()` in `lib/webhooks/deliver.ts` (signed, retried by the cron tick; never throws into a run).
- **KMPlus products** are destinations through the Nexus Ingest Contract (`docs/integrations/kmplus-ingest-contract.md`, driver `lib/connectors/drivers/kmplus.ts`, reference mock `scripts/test/kmplus-mock.ts`); records the product refuses go to the quarantine at the destination step. Change the contract only with a new version.
- **Outbound requests to user-supplied URLs** (OIDC discovery, webhooks) must use `safeFetch` / `assertPublicHttpsUrl` (`lib/net/safe-url.ts`): https only, no private/internal addresses, no redirects. Local tests may set `NEXUS_ALLOW_PRIVATE_URLS=true` (ignored in production).
- **Catalog** (`app/actions/catalog.ts`): items are derived from datasets + source schema scans; `catalog_entries` stores documentation and live/cached access. Cached tables are managed pipelines (`lib/pipelines/managed.ts`) writing a dataset named after the table's alias; never let a cache overwrite a dataset another pipeline writes.
- **No new mock data.** Many dashboard layers are still hardcoded UI (PRD §10). Turning a mock layer real means: table → server actions → load in the layer → empty/loading/error states.
- **Connectors:** add the slug in `lib/connectors/types.ts`, the definition in `lib/connectors/catalog.ts`, the driver in `lib/connectors/drivers/<slug>.ts`, dispatch cases in `lib/connectors/runtime.ts` (test / scan / sample), **and a case in `scripts/connector-harness.ts`** (it warns about catalog connectors without one). Throw `NonRetryableError` (`lib/pipelines/io.ts`) for configuration problems so runs don't retry them. While `CONNECTOR_BILLING_ENABLED` isn't `true`, every connector installs free. Full recipe in PRD §14.3.
- **Email:** everything goes through `sendEmail()` in `lib/email.ts` (SMTP: `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD`, `EMAIL_FROM`; the company mail server `mail.kmplus.co.id:465` as `noreply@kmplus.co.id`, set in all Vercel environments). Without SMTP, development prints emails to the server console and production skips email verification.
- **Approvals & environments:** a workspace's `publishApproval` (off / destructive / always) decides whether a publish waits for a second person (`lib/pipelines/approvals.ts`, `pipeline_approvals`, `app/actions/approvals.ts`); every publish path goes through `publishOrRequest()` in `lib/pipelines/publish.ts` (also home of `savePipelineAs` / `publishVersion`). Environments (GV-7) are workspaces linked by `environmentGroupId` (dev → staging → prod); `promotePipeline` (`app/actions/environments.ts`, pure planning in `lib/pipelines/promote.ts`) copies the published version and maps data sources and rules by name and chained pipelines by `pipelines.promotionKey`. A locked workspace (`environmentLocked`, Production by default) rejects direct pipeline edits (`assertPipelinesEditable`).
- **Auth:** sign-up requires email verification (when email works) and **every account must enroll TOTP 2FA** (Better Auth `twoFactor` plugin; `/setup-2fa`, `/verify-2fa`). `requireSession()` rejects accounts without 2FA unless the session came from SSO (`session.authMethod = 'sso'`); server pages use `requirePageUser(next)`. Logins and 2FA enrollment are audited by a Better Auth plugin in `lib/auth.ts`. **SSO** (OIDC or SAML 2.0: Entra ID, Google, Okta, others) uses `@better-auth/sso` with domain verification; SAML providers store the IdP entity ID, sign-in URL and certificate from metadata (`lib/auth/saml.ts`, ACS `/api/auth/sso/saml2/sp/acs/<providerId>`); provider secrets in `ssoProvider.oidcConfig`/`samlConfig` are sealed with the workspace key (`sealSsoConfig` in `lib/security/credentials.ts`) and opened for Better Auth by `SsoConfigPlugin` (`lib/auth/sso-config-plugin.ts`, a Kysely plugin on the auth database), never written plain; its provider-management endpoints are disabled (`disabledPaths`): workspace admins manage providers in `app/actions/sso.ts` (DNS TXT `_nexus-sso.<domain>`), sign-ins auto-join the provider's workspace (`lib/auth/sso.ts`; off when `jitProvisioning` is false, and never for someone SCIM deactivated), and "require SSO" blocks password sign-in for the domain. **SCIM 2.0** (`/api/scim/v2`, `lib/scim/*`, tokens `nxs_…` hashed in `scim_tokens`) provisions accounts at verified SSO domains; deactivation removes membership and deletes the person's sessions; groups mapped to a role set members' roles (highest wins; never removes the last admin).
- **Alerts:** failed runs (and rejected rows, if the pipeline opts in) create a `notifications` row (bell icon) via `lib/notifications.ts`, plus one email when SMTP is configured. Alerting must never fail a run.
- **Production errors** are hidden behind a digest. Read the real message with `vercel logs kmplus-nexus-platform.vercel.app --scope irfanalfieris-projects`.
- **Pipelines:** the definition format is the zod schema in `lib/pipelines/definition.ts` (shared by UI and engine; keep it client-safe): a graph `{schemaVersion: 2, nodes, edges, settings}` (v1 step lists are normalized on read). `pipelines.config` is the **published** version that runs; saves go to `draftConfig` until published (`publish` flag / `publishPipeline`). Conditions and expressions (`ConditionGroup`, `Expr`, evaluated in `conditions.ts`) are shared with business rules (`lib/rules/*`, `applyRules` in `lib/rules/evaluate.ts`). Quarantine rows (`pipeline_run_rejects`: kind invalid/approval/flag, status open/fixed/approved/replayed/dismissed/superseded) are replayed by `enqueueRun(…, 'replay', { replayIds })`, which re-enters the graph at the step that held them. A finished full run supersedes older open rows of its pipeline (fixes and approvals carry over to identical new rows); a replay into a replace dataset with keys replaces rows by key (`writeDataset({ replaceKeys })`). Run triggers: manual, schedule, replay, api, webhook (`/api/hooks/pipelines/<id>/<token>`, token hash on `pipelines.triggerTokenHash`), chain (schedule type `after`: `runDependents()` in `jobs.ts` queues pipelines scheduled after a finished one; saves reject loops). After each run the worker records a daily dataset quality snapshot (`lib/quality/snapshot.ts`) and emits webhook events. Map lookups (`lookup` transform) load dataset key→value tables in `loadRunContext`. Pipeline and mapping templates live in `lib/pipelines/templates.ts` (pure, tested). `engine.ts`, `transforms.ts` and `columns.ts` are pure (covered by `scripts/engine-tests.ts`); all I/O lives in `io.ts`; Runs execute in the background worker `jobs.ts` (Monitoring can cancel queued/running jobs and retry finished runs): `enqueueRun()` queues (one active job per pipeline), `processJobs()` claims jobs with leases and runs 5,000-row chunks, checkpointing after each (resumes across invocations, retries from the checkpoint, advances incremental watermarks in `pipelines.state` only after the whole run succeeds). Start a worker with `startWorker()` / `nudgeWorker()` (`lib/pipelines/worker.ts`, uses `after()`), never run a pipeline inline in a request. `runner.ts` keeps test runs, summaries and alerts. Timestamps without a zone are always treated as UTC. Postgres/MySQL reads pass column types from the driver (`ChunkRead.types`) so datasets keep numeric and date types; the Nexus pool returns DATE as `YYYY-MM-DD` text. Writes to customer databases only go to data sources added as destinations, never create or truncate their tables. Scheduling is Supabase pg_cron (`drizzle/0013_scheduler_retention.sql`, fires when a pipeline is due, a job waits or a retention check is due) calling `/api/cron/pipelines` with `CRON_SECRET`, which must match the Vault secret `nexus_cron_secret`.
- **DB TLS:** `lib/db/index.ts` and `scripts/db-ssl.mjs` verify the server certificate against the bundled Supabase root CA (`lib/db/supabase-ca.ts`, or `DATABASE_CA_CERT`); only localhost connects without TLS. Postgres data sources choose verify / require / disable (+ CA); Supabase hosts are always verified.
- **Type errors fail the build.** Run `pnpm typecheck` before pushing.
