# KMPlus Nexus

Enterprise integration platform (EiPaaS): connect, transform, govern, and distribute enterprise data (HR-first) for KMPlus products (KMS, LMS, TMS, PMS, CMS, IMS) and third-party systems.

**Read [docs/PRD.md](docs/PRD.md) before building a feature.** It defines the product, the glossary (§5), the requirements per layer with IDs (§7), what's real and what's still mock (§10), the target architecture (§11), and the build rules (§14). When a feature moves from mock to real, update the §10 status table in the same change.

## Stack
Next.js 16 (App Router) · React 19 · TypeScript · Tailwind v4 + shadcn/ui · Better Auth · Drizzle ORM on Supabase Postgres (project `kissurqzqwvkvwcyfbhc`, Tokyo, via the transaction pooler) · deployed on Vercel (push to `main` auto-deploys).

**Databases:** Production uses the `postgres` database; Preview and Development (and therefore `.env.local`) use the separate `nexus_dev` database on the same Supabase server, with their own `NEXUS_ENCRYPTION_KEY`. To migrate production, run `db-migrate` with `DATABASE_URL` set to the production URL (same as dev with `/postgres` instead of `/nexus_dev`). Production `DATABASE_URL` is a sensitive Vercel variable and can't be pulled. Dev and preview have no scheduler.

**Checks before pushing:** `pnpm typecheck`, `pnpm test:engine`, `pnpm test:integration`, `pnpm build` (CI runs the same on every push and PR; integration tests run against a Postgres service container).

## Rules
- **pnpm only.** After any dependency change, commit `pnpm-lock.yaml`. Vercel installs with `--frozen-lockfile`, so a stale lockfile fails the deploy.
- **Schema changes:** edit `lib/db/schema.ts`, run `DATABASE_URL=postgres://unused npx drizzle-kit generate --name <change>` (or `--custom` for hand-written SQL), commit the SQL in `drizzle/`, then apply with `scripts/db-migrate.mjs --apply`. Never apply migrations by hand, or the tracking table falls out of sync. **Never edit a migration that has been applied**: `db-migrate` stores a checksum and refuses to run if an applied file changed; put the change in a new migration. Every new table needs `ALTER TABLE ... ENABLE ROW LEVEL SECURITY` (see `drizzle/0001_enable_rls.sql`): Supabase exposes `public` through its REST API, and RLS without policies blocks that while the app (connecting as `postgres`) is unaffected. Column names are camelCase and must be quoted in raw SQL (`"userId"`). Unquoted SQL creates lowercase columns and breaks Drizzle queries.
- **Server actions return errors as values.** Next.js production hides the message of any error thrown from a server action, so every exported action in `app/actions/*` is a thin wrapper `export async function x(...args) { return guard(() => xImpl(...args)) }` (`lib/server-action.ts`) around a throwing `xImpl`. **Client components (and server pages) import actions from `@/lib/actions/<file>`**, which throws the error again with its real message; never import `@/app/actions/*` from UI code. Server code that needs another action's logic calls a helper in `lib/` (e.g. `lib/connectors/install-check.ts`), not the exported wrapper. New action: write `async function fooImpl`, add the wrapper at the bottom, add `foo` to `lib/actions/<file>.ts`.
- **Workspaces & permissions:** all shared data belongs to a workspace (`workspaceId` column); `userId` only records who created or acted. Every server action starts with `const ctx = await requireWorkspace('<permission>')` (or no argument for read-only), validates every argument with zod, **scopes every query by `ctx.workspaceId`**, records mutations and views of real data with `recordAudit(ctx, { action, resource, resourceId, changes, diff })` from `lib/audit.ts` (adds IP + user agent; never put secret values in `changes`; for updates pass `diff: diffObjects(before, after)` from `lib/audit-diff.ts`, which records secrets only as "changed"), then `revalidatePath('/dashboard', 'layout')` (every screen is its own route under `/dashboard`). Permissions and roles live in `lib/auth/permissions.ts` (client-safe); the UI hides controls with `useCan(permission)` from `components/workspace/workspace-context.tsx`, but the server check is the real one. Create ids with `newId('prefix')` (UUID), never `Date.now()`. New tables holding workspace data need `workspaceId` + an index. Dataset physical tables are named per workspace; existing ones keep their stored `tableName`.
- **Credentials:** `data_sources.credentials` is encrypted with AES-256-GCM via `lib/security/credentials.ts` (`encryptCredentials(id, obj, workspaceId)` on write, `decryptCredentials(id, stored)` on read). Envelopes are v2: sealed with a per-workspace key derived (HKDF) from the master key and bound to the source and workspace; v1 rows still decrypt and upgrade on re-save or `reencrypt-credentials`. File Upload sources hold only a server-assigned `storageKey` (never accept one from the browser). Never return credentials to the client, never log them. Requires `NEXUS_ENCRYPTION_KEY` (32 bytes, base64). Envelopes carry a key id; to rotate, set the new key, move the old one to `NEXUS_ENCRYPTION_KEY_PREVIOUS`, deploy, run `scripts/reencrypt-credentials.mjs --apply`, then drop the old key. Custom credential forms (REST, Salesforce) are edited with secrets masked as `KEEP` (`lib/connectors/secret-mask.ts`); add new secret fields there.
- **Governance:** dataset policies (`dataset_policies`, `lib/governance/*`) classify and mask columns and hold **row-level filters per role** (`lib/governance/row-filters.ts`). Any code that returns dataset rows must use `accessFor(workspaceId, dataset, role)` (masks + row filters) with `applyMasks` and pass `rowFilters` to `readDatasetSample` / SQL builders; live source rows use `liveTableAccess`. Roles with `data:unmasked` (admin, steward) see real values. Analytics passes masked columns as `blockedColumns` and `rowFilters`. Datasets have system columns `_nexus_id`, `_nexus_loaded_at`, `_nexus_run_id`, `_nexus_deleted_at`, `_nexus_chunk`: every read excludes soft-deleted rows and never returns system columns. Appends pass `runId` + `chunk` to `writeDataset` so a resumed chunk replaces its earlier copy (exactly-once). Retention runs hourly from the cron tick.
- **Defined dataset schemas** (`lib/datasets/schema.ts` pure and engine-tested, `store.ts` / `write.ts` server, `app/actions/schemas.ts`, `components/catalog/dataset-schema.tsx`, `components/pipelines/schema-mapping.tsx`): a defined dataset (`dataset_schemas`, `nexus_datasets.defined`) owns its columns; its Destination steps map target first (`columnMap`, `dropExtra`) and write only mapped columns, upserting on the schema keys. Change a schema only through `changeSchema` (versions, aliases, policy sync, rename propagation, audit, webhook), never by altering its table; renames keep a 30-day alias that published pipelines (`followRenames`) and the Data API honour. Auto-added columns stay out of the Data API until reviewed (`exposedColumns`). Promotion carries schemas (`schemaPromotion`, additive only). New upgrade notices go in `lib/upgrades/notices.ts` with `UpgradeBanner`.
- **Source health & drift** (DS-7/DS-8): `lib/connectors/health.ts` (server) runs every check: the cron tick's `runDueHealthChecks` (sources whose `nextHealthCheckAt` is due; `healthCheckMinutes`, 0 = off; ≤ 60 s per tick), "Test connection" and credential saves. Every new schema scan goes through `recordScan` (never write `config.schemaScan` directly), which diffs it with the previous scan (`lib/connectors/drift.ts`, pure and tested) and keeps breaking changes in `data_sources.schemaDrift` with the pipelines they reach until reviewed. History in `source_health_checks` (30 days). Alerts go to people with `sources:manage` on the first failure, on recovery and on drift.
- **Run diagnostics & retention:** failed runs get a rule-based root-cause hint (`rootCause` in `lib/monitoring/root-cause.ts`, pure and tested; copy in the `hints` namespace; also in failure alerts) before any AI diagnosis; add a pattern there for a new error family. Run logs follow the workspace's `logDetailDays` / `runSummaryDays` (`lib/monitoring/log-retention.ts`, hourly from the cron tick): details (log lines, stack) are stripped, then whole runs removed unless they still hold open Data quality rows.
- **Analytics:** widget specs are `lib/analytics/definition.ts` (client-safe); `buildWidgetSql` (`lib/analytics/query.ts`, pure, tested) only accepts dataset column names and binds every value. Queries run read-only with a 15 s statement timeout. DB-3: a widget may `join` a second dataset on a key (`join:<column>` refs; the joined side is `DISTINCT ON` the key, latest `_nexus_loaded_at`, so rows never multiply); `runWidget` passes that dataset's masks and row filters too. DB-5: `dashboards.sharing` (workspace / restricted roles + people; check with `visibleDashboard` in `app/actions/analytics.ts`); embed links (`dashboard_embeds`, token `nxe_…` hashed, roles viewer/analyst only, `loadEmbed` in `lib/analytics/dashboards.ts`, page `app/embed/dashboards/[token]`, CSP `frame-ancestors` set in `proxy.ts`); Export PDF is the print page `app/print/dashboards/[id]`, PNG is drawn client-side (`lib/analytics/png.ts`). Dashboard-wide filters (DB-4, `dashboards.filters`) become ordinary widget filters through `applyDashboardFilters` in `runWidget`; value choices come from `distinctValues` (masks and row filters applied). Charts follow the data-viz rules in `components/analytics/charts.tsx` (slot-1 blue, table view for every chart).
- **Data API** (`/api/v1/*`, `lib/api/*`): Bearer keys `nxk_…` (only a SHA-256 hash stored, `lib/api/keys.ts`), scopes `datasets:read` / `domains:read` / `pipelines:run` / `runs:read`, read as the key's role (masks + row filters). Every route goes through `handle()` in `lib/api/serve.ts` (auth, per-key rate limit with X-RateLimit headers, JSON errors). Query parsing and SQL are pure (`lib/api/query.ts`, tested); every read is audited as `API_READ`. Never expose a dataset column that isn't in its column list. Update `lib/api/openapi.ts` (served at `/api/v1/openapi.json`) with every endpoint change. Outbound webhooks: `emitEvent()` in `lib/webhooks/deliver.ts` (signed, retried by the cron tick; never throws into a run).
- **REST API destinations** (destination node `kind: 'api'` in `lib/pipelines/definition.ts`, writer `lib/connectors/rest/write.ts`, server/agent only): the data source (role destination) supplies base URL, sign-in, headers, variables and Network settings (`buildRestWriteBase` in `rest-client.ts`, every URL kept under the base URL); the step holds method, path (`{{column}}` values URL-encoded; `.`/`..` refused) and the body as a `BodyNode` tree built from a pasted JSON / form / XML example. Rendering, sample parsing (small XML reader, no DTD/entities), auto-binding, response refused-item extraction and retry classification are pure in `lib/pipelines/body-template.ts` (engine-tested): never add a string template language. A list with `items: 'rows'` is batch mode (one per request); nested `items: 'row'` takes one item from the row (phase 2 adds grouping as another `items` value). 2xx = written (minus refused items), other 4xx → quarantine via `checkText('apiRefused' | 'apiItemRejected')` with `shortApiMessage` (redacted), 408/429/5xx retried (`API_MAX_ATTEMPTS`, Retry-After), 401/403/redirect/404-for-all throw non-retryable. Batch ids `runId:chunk:batch` are stable (idempotency key); `apiChunkRows` caps the chunk so a slice finishes; never log request bodies. Agent-backed REST destinations go through the `apiWrite` op (agent 1.3.0+, `MIN_AGENT_VERSION_FOR_OP`). The editor's test request is `sendApiTestRequest` (audited `TEST_REQUEST`, sign-in masked with `redactRestRequest`). Test locally with `scripts/rest-write-mock.ts`.
- **KMPlus products** are destinations through the Nexus Ingest Contract (`docs/integrations/kmplus-ingest-contract.md`, driver `lib/connectors/drivers/kmplus.ts`, reference mock `scripts/test/kmplus-mock.ts`); records the product refuses go to the quarantine at the destination step. Change the contract only with a new version.
- **Outbound requests to user-supplied URLs** (OIDC discovery, webhooks) must use `safeFetch` / `assertPublicHttpsUrl` (`lib/net/safe-url.ts`): https only, no private/internal addresses, no redirects. **Connector HTTP requests** (REST, SAP, Talenta, KMPlus products, OAuth token URLs) go through `connectorFetch` / `assertConnectorUrl`: http or https, private and intranet addresses refused from the cloud with a pointer to the Nexus Agent, every redirect target checked; it also applies a client certificate / company CA (undici dispatcher) and request signing (`X-Nexus-Signature`, `lib/net/request-signing.ts`) for APIs published by hand. Inside the agent every task runs in `withPrivateNetworkAccess`; a self-hosted Nexus sets `NEXUS_PRIVATE_NETWORK_ACCESS=true`; `NEXUS_EGRESS_IPS` lists fixed outbound IPs when a deployment has them. Local tests may set `NEXUS_ALLOW_PRIVATE_URLS=true` (ignored in production). Guide: `docs/integrations/intranet-apis.md`.
- **Catalog** (`app/actions/catalog.ts`): items are derived from datasets + source schema scans; `catalog_entries` stores documentation and live/cached access. Cached tables are managed pipelines (`lib/pipelines/managed.ts`) writing a dataset named after the table's alias; never let a cache overwrite a dataset another pipeline writes.
- **UI & design system:** read [DESIGN.md](DESIGN.md) before building a screen (KM+ “mimic panel”: tokens in `app/globals.css`, IBM Plex, flat panels, one layer above the board). Use colour **tokens only** (`bg-card`, `text-muted-foreground`, state tokens `live` / `danger` / `warning` / `held` / `info` / `paused` with `-text` and `-soft` variants), never raw palette classes or hex. Build with the shared blocks: `Modal` / `ConfirmDialog` / `useConfirm` (`components/ui/dialog.tsx`; every destructive or outward action confirms, editors pass `dirty`), `Notice`, `EmptyState`, `Table`/`DataTable`, `FlowLine` / `StateMark` (state = mark + words, never colour alone), `useToast` (undo), `PageHeader` (the page’s only h1), `SettingsPanel` + `nativeSelectClass` (`components/workspace/settings-panel.tsx`). Every screen has a URL: `app/dashboard/<section>/page.tsx` with `generateMetadata = () => sectionMetadata('<section>')`; navigation lives in `lib/navigation.ts` (groups, settings tabs, landing by role). Interface text is bilingual: add strings to `lib/i18n/messages/en.ts` **and** `id.ts`, or for a screen to its namespace pair `lib/i18n/messages/en/<ns>.ts` + `id/<ns>.ts` (same shape, compiler- and `engine-tests`-checked; plurals `{count, plural, one {# row} other {# rows}}`) and read them with `useT()` / `usePrefs()` (also `formatDateTime`, `formatNumber`; times in WIB); server code uses `getTranslator()` from `lib/i18n/server.ts`. Theme and language are cookies (`nexus_theme`, `nexus_lang`) read in `app/layout.tsx`. WCAG 2.2 AA: label every control, `aria-label` icon buttons, keyboard-operable rows.
- **Guide me & Help** (`components/tour/guided-tour.tsx`, `lib/tour/steps.ts`, `components/help/*`, `lib/help/*`, `/dashboard/help`): tour steps point at controls marked `data-tour="…"` (keep the marker when you rework a screen; `engine-tests` checks every step's marker exists) with copy in the `tour` namespace. The guide's text lives in `lib/help/content/{en,id}.ts` as chapters → sections → blocks (the page numbers them 1, 1.1 … from their order; same ids and block shapes in both languages, compared by `engine-tests`), followed by the FAQ as a separate part; diagrams in `components/help/diagrams.tsx` (tokens only; the roles matrix reads `lib/auth/permissions.ts`). When a feature changes what a chapter says, update both languages in the same change; when a screen's look changes, re-run `scripts/capture-help-screens.mjs` (real captures of the fictional demo workspace only, never real customer data).
- **Check messages** (Validate rules, Map conversions, manager checks, approval holds) come from one table in `lib/pipelines/check-messages.ts`: the engine writes the English text with `checkText(code, params)` (stored rows stay readable), and the UI shows any stored message with `localizeCheck(message, locale)`; add new checks there, never as inline strings. Server step titles shown in the UI go through `localizeStepTitle` (`components/pipelines/step-title.ts`).
- **Server error messages** are thrown in English and translated for the caller by `guard()` (`lib/server-action.ts` → `localizeServerError` in `lib/i18n/server-errors.ts`). Every message thrown in `app/actions` or `lib` (and every zod custom message) needs an entry in `lib/i18n/server-errors-table.ts` with `{pN}` for runtime values; `engine-tests` scans the code and fails on a missing one. Data API (`/api/v1`) errors stay English.
- **Emails** use the one branded layout in `lib/email.ts` (`render`: KM+ logo band, teal button, details table, plain-text twin); build each email in `lib/email-templates.ts` with copy in `lib/i18n/messages/{en,id}/email.ts`, in the language of the request (`requestLocale()`, English for background work). Never put secrets or personal data beyond the recipient's own in an email.
- **AI connector suggestions and catalog search** (AI-4/AI-5, `lib/ai/discovery.ts`, pure and tested): rules and synonym ranking answer first and work without a model; a model only fills in (AI-4) or re-ranks a shortlist (AI-5), and its answer must name real connectors / catalog items (invented columns dropped). Pasted text is scrubbed (`scrubPasted`); catalog search sends names, docs and column names, never rows.
- **AI pipeline drafts and diagnosis** (AI-2/AI-3, `lib/ai/pipelines.ts`, pure and tested): the model fills a small plan or a diagnosis that is checked against real sources/tables and the pipeline definition; drafts open in the editor unsaved, fixes save a draft version (never publish); diagnosis prompts carry redacted check messages (`redactMessage`), never row values.
- **No new mock data.** Many dashboard layers are still hardcoded UI (PRD §10). Turning a mock layer real means: table → server actions → load in the layer → empty/loading/error states.
- **Writable connectors** are listed in `WRITABLE_CONNECTORS` (`lib/pipelines/io.ts`) and `WRITABLE` in `components/pipelines/step-editors.tsx` (keep them equal); data sources added as destinations of any other type show greyed out in the Destination step.
- **Connectors:** add the slug in `lib/connectors/types.ts`, the definition in `lib/connectors/catalog.ts` (with its `group`: the Connectors screen's category, and search `keywords` in English and Indonesian; search and grouping are pure in `lib/connectors/search.ts`), its capabilities in `lib/connectors/capabilities.ts` and the permissions it needs in `lib/i18n/messages/{en,id}/connectorDocs.ts` (the detail page `/dashboard/connectors/<slug>`; engine-tested), the driver in `lib/connectors/drivers/<slug>.ts`, dispatch cases in `lib/connectors/runtime.ts` (test / scan / sample), **and a case in `scripts/connector-harness.ts`** (it warns about catalog connectors without one). Throw `NonRetryableError` (`lib/pipelines/io.ts`) for configuration problems so runs don't retry them. While `CONNECTOR_BILLING_ENABLED` isn't `true`, every connector installs free. Full recipe in PRD §14.3.
- **Secrets managers** (DS-13: `vault`, `awssecrets`, `azurekeyvault`, `gcpsecrets`, `doppler`; drivers in `lib/connectors/drivers/*`, table in `lib/secrets/managers.ts`) are credential providers, never data: their scan has no tables, sampling/reading throws, and `isSecretManager()` (`lib/secrets/types.ts`) keeps them out of the pipeline editor (`getBuilderOptions`), catalog and AI drafts. Credentials anywhere may hold `{{secret:<manager name>:<path>#<field>}}`; resolve with `resolveSecretRefs(workspaceId, creds)` / `withResolvedSecrets(source)` (`lib/secrets/resolve.ts`, server-only) **right before a driver call** (already done in `runner.ts loadSource`, catalog live samples, Data API live tables, data-source and connector-source actions) and **never save resolved values** (save paths keep the references). Values are cached ≤ 60 s in memory only. **Infrastructure** connectors (Prometheus, Elasticsearch/OpenSearch, Datadog, New Relic, Grafana; S3-compatible, Azure Blob, GCS through `lib/connectors/storage/files.ts`) are read-only sources sharing `lib/connectors/http.ts`; cloud sign-in without SDKs in `lib/net/aws-sigv4.ts` (checked against AWS's example) and `lib/net/cloud-auth.ts`; pipeline reads with their own path go through `readConnectorRows` in `runtime.ts`. `scripts/test/infra-mock.ts` stands in for all 13 services (and for Microsoft Graph, Google Sheets / Drive, a GraphQL API and a SOAP service). **Productivity, file transfer and other APIs** (DS-9): `sharepoint` (Graph: `lists/<name>` and `files/<path>` tables, app registration via `azureAccessToken`), `googlesheets` (tabs), `googledrive` (a `StorageClient`; Sheets exported as CSV), `sftp` (ssh2, loaded with `loadSsh2()`; `assertConnectorHost` from the cloud, host key pinning; `serverExternalPackages` in `next.config.mjs`; `scripts/test/sftp-mock.ts`), `graphql` and `soap` (operations under `### name` lines, records and faults pure in `lib/connectors/api-records.ts`). Credential fields may be `type: 'textarea'` for multi-line values. Guide: `docs/integrations/infrastructure-and-secrets.md`.
- **Email:** everything goes through `sendEmail()` in `lib/email.ts` (SMTP: `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD`, `EMAIL_FROM`; the company mail server `mail.kmplus.co.id:465` as `noreply@kmplus.co.id`, set in all Vercel environments). Without SMTP, development prints emails to the server console and production skips email verification.
- **Nexus Agent (#13)** (`agent/`, `lib/agent/*`, `app/api/agent/v1/*`, `app/actions/agents.ts`): an outbound-only program in the customer's network (Node 20+, single file built by `scripts/build-agent.mjs` into `public/downloads/`, gitignored, built before `next build`). Agent-backed data sources have `config.agent = { agentId, connection }` and no credentials; `lib/pipelines/io.ts` (reads, writes, live queries) and `lib/agent/sources.ts` (test/scan/sample) send them to the agent with `callAgent()` (queues an `agent_tasks` row and waits; always pass the data source's `workspaceId`). Only `addAgentDataSource` may set `config.agent`; `createDataSource` strips it. **Intranet APIs** (DS-12): an agent `rest` connection holds the base URL and sign-in; an agent-backed REST data source stores only the request design (its credentials, edited in the REST form in agent mode) and every call sends it as `request` (`agentRestRequest`); the agent merges it with `mergeAgentRestRequest` (`lib/connectors/rest/agent-request.ts`: agent-owned fields always win, requests stay under the base URL, no redirects). Designed requests need agent 1.2.0+, REST writes (`apiWrite`) 1.3.0+, Enrich / "Changes data" calls (`apiCall`) 1.4.0+ (`callAgent` refuses older agents; per-op minimums in `MIN_AGENT_VERSION_FOR_OP`). The REST form's client-safe pieces live in `lib/connectors/rest/config.ts`; `rest-client.ts` is server/agent only. The agent runs tasks with the same driver and I/O code (`lib/agent/execute.ts`), so keep `lib/pipelines/io.ts` free of request-only APIs.
- **AI assistant (#14)** (`lib/ai/*`, `app/actions/ai.ts`, `components/ai/*`): open-source models only, via any OpenAI-compatible API (`lib/ai/llm.ts`): the server's model (`NEXUS_AI_BASE_URL`, `NEXUS_AI_MODEL`, optional `NEXUS_AI_API_KEY`) or a model next to an agent (`workspaces.aiProvider` server / agent / off). Prompts carry schemas and examples only for public columns (`safeSamples`); every answer goes through a check in `lib/ai/prompts.ts` (real columns, editor schemas) with one repair round (`askModel`); AI output is a draft the user reviews; questions run through `runWidget` (`lib/analytics/run.ts`) with the asker's masks. Audit `AI_ASSIST` without prompt text.
- **Run recovery, version compare, maintenance windows** (MN-4, VC-3, SC-4): a run that fails inside the read/write loop keeps its checkpoint and staging for `RESUMABLE_HOURS` (48) (`progress.resumableUntil`); `retryPipelineRun(id, 'resume')` → `resumeRun` reopens the same job, `'restart'` queues a new run; the cron tick drops expired staging (`expireResumableRuns`). Version diffs are pure in `lib/pipelines/version-diff.ts` (`compareVersions` action, History → Compare). Maintenance windows (`maintenance_windows`, pure `lib/pipelines/maintenance.ts`, WIB, weekly with overnight or once) hold only scheduled and chained runs: the cron tick calls `holdDuePipeline` (`maintenance-store.ts`) and `runDependents` checks `holdRun`; never hold manual, webhook or API runs.
- **Approvals & environments:** a workspace's `publishApproval` (off / destructive / always) decides whether a publish waits for a second person (`lib/pipelines/approvals.ts`, `pipeline_approvals`, `app/actions/approvals.ts`); every publish path goes through `publishOrRequest()` in `lib/pipelines/publish.ts` (also home of `savePipelineAs` / `publishVersion`). Changes to defined dataset schemas follow the same policy (`schemaApprovalReasons`): `changeDatasetSchema` opens a request (`pipeline_approvals.subject = 'schema'`, operations in `payload`, `lib/datasets/approval.ts`) instead of applying; approving re-checks the operations against the current schema and applies them as the requester's change, or supersedes the request. Runs' automatic additions and promotions call `changeSchema` directly and never wait. Pipeline JSON export / import (VC-5: `lib/pipelines/transfer.ts` pure and tested, `app/actions/pipeline-transfer.ts`) reuses the promotion planner (`planImport` → `planPromotion`, workspace sides from `promotionSide()`); exports never carry credentials. Environments (GV-7) are workspaces linked by `environmentGroupId` (dev → staging → prod); `promotePipeline` (`app/actions/environments.ts`, pure planning in `lib/pipelines/promote.ts`) copies the published version and maps data sources and rules by name and chained pipelines by `pipelines.promotionKey`. A locked workspace (`environmentLocked`, Production by default) rejects direct pipeline edits (`assertPipelinesEditable`).
- **Terms and Conditions** (`lib/legal/*`, `/terms`, `/accept-terms`, `terms_acceptances`): every account accepts the current `TERMS_VERSION` once, on the sign-up form (the Better Auth plugin in `lib/auth.ts` refuses a sign-up without `acceptedTerms` and records it) or on `/accept-terms` (`requirePageUser` sends people there before 2FA setup; `requireSession` refuses actions until accepted). To change the terms, edit both `lib/legal/terms-content/{en,id}.ts` (same section ids, engine-tested; the Indonesian version prevails) and set `TERMS_VERSION` to the new effective date: everyone accepts again. Test users need `recordTermsAcceptance` (integration tests and the demo seed do it). `proxy.ts` passes the requested dashboard path (`x-nexus-path`) so the gates return there.
- **Auth:** sign-up requires email verification (when email works), **forgot password** is Better Auth's reset (`emailAndPassword.sendResetPassword` / `onPasswordReset` in `lib/auth.ts`, screens in `components/password-reset.tsx`; never reveal whether an account exists, sessions are revoked, a "password changed" email and a PASSWORD_RESET audit entry follow; SSO-required domains are refused by `enforceSso`), **invite links work without an account** (`/invite/<token>` signed out: `createAccountFromInvite` in `app/actions/workspaces.ts` creates the account for the invited email, marked verified because the emailed link proves it, records the terms; then sign-in → 2FA setup → `?welcome=1` joins automatically; existing accounts get "Sign in to join", SSO-required domains "Continue with SSO"), and **every account must enroll TOTP 2FA** (Better Auth `twoFactor` plugin; `/setup-2fa`, `/verify-2fa`). `requireSession()` rejects accounts without 2FA unless the session came from SSO (`session.authMethod = 'sso'`); server pages use `requirePageUser(next)`. Logins and 2FA enrollment are audited by a Better Auth plugin in `lib/auth.ts`. **SSO** (OIDC or SAML 2.0: Entra ID, Google, Okta, others) uses `@better-auth/sso` with domain verification; SAML providers store the IdP entity ID, sign-in URL and certificate from metadata (`lib/auth/saml.ts`, ACS `/api/auth/sso/saml2/sp/acs/<providerId>`); provider secrets in `ssoProvider.oidcConfig`/`samlConfig` are sealed with the workspace key (`sealSsoConfig` in `lib/security/credentials.ts`) and opened for Better Auth by `SsoConfigPlugin` (`lib/auth/sso-config-plugin.ts`, a Kysely plugin on the auth database), never written plain; its provider-management endpoints are disabled (`disabledPaths`): workspace admins manage providers in `app/actions/sso.ts` (DNS TXT `_nexus-sso.<domain>`), sign-ins auto-join the provider's workspace (`lib/auth/sso.ts`; off when `jitProvisioning` is false, and never for someone SCIM deactivated), and "require SSO" blocks password sign-in for the domain. **SCIM 2.0** (`/api/scim/v2`, `lib/scim/*`, tokens `nxs_…` hashed in `scim_tokens`) provisions accounts at verified SSO domains; deactivation removes membership and deletes the person's sessions; groups mapped to a role set members' roles (highest wins; never removes the last admin).
- **Alerts:** failed runs (and rejected rows, if the pipeline opts in) create a `notifications` row (bell icon) via `lib/notifications.ts`, plus one email when SMTP is configured. Alerting must never fail a run. MN-5: alert channels (`alert_channels`: Slack / Teams / signed webhook, URL sealed with `encryptCredentials`, sent with `safeFetch`, payloads pure in `lib/alerts/rules.ts`) and per-pipeline settings (`pipeline_alerts`: subscribers, channels, error-rate %, max duration, stale hours) go through `deliverAlert` in `lib/alerts/send.ts` from `alertIfNeeded` (runner.ts); SLA alerts come from `checkAlertSlas` in the cron tick (`nextCheckAt`, state keeps each alert to once). Never return a channel URL to the client (only its host).
- **Production errors** are hidden behind a digest. Read the real message with `vercel logs kmplus-nexus-platform.vercel.app --scope irfanalfieris-projects`.
- **Pipelines:** the definition format is the zod schema in `lib/pipelines/definition.ts` (shared by UI and engine; keep it client-safe): a graph `{schemaVersion: 2, nodes, edges, settings}` (v1 step lists are normalized on read). `pipelines.config` is the **published** version that runs; saves go to `draftConfig` until published (`publish` flag / `publishPipeline`). Conditions and expressions (`ConditionGroup`, `Expr`, evaluated in `conditions.ts`) are shared with business rules (`lib/rules/*`, `applyRules` in `lib/rules/evaluate.ts`). Quarantine rows (`pipeline_run_rejects`: kind invalid/approval/flag, status open/fixed/approved/replayed/dismissed/superseded) are replayed by `enqueueRun(…, 'replay', { replayIds })`, which re-enters the graph at the step that held them. A finished full run supersedes older open rows of its pipeline (fixes and approvals carry over to identical new rows); a replay into a replace dataset with keys replaces rows by key (`writeDataset({ replaceKeys })`). Run triggers: manual, schedule, replay, api, webhook (`/api/hooks/pipelines/<id>/<token>`, token hash on `pipelines.triggerTokenHash`; SC-6 event adapters in `lib/pipelines/events.ts` (pure): CloudEvents / SAP Event Mesh handshake (OPTIONS), Event Grid validation, Graph `validationToken` + hashed `clientState`, type filters and `pipeline_trigger_events` de-dup in `pipelines.triggerConfig`; an event during a run sets `eventPendingAt` and `runPendingEvent` queues one follow-up run), chain (schedule type `after`: `runDependents()` in `jobs.ts` queues pipelines scheduled after a finished one; saves reject loops). After each run the worker records a daily dataset quality snapshot (`lib/quality/snapshot.ts`) and emits webhook events. Map lookups (`lookup` transform) load dataset key→value tables in `loadRunContext`. Pipeline and mapping templates live in `lib/pipelines/templates.ts` (pure, tested). `engine.ts`, `transforms.ts` and `columns.ts` are pure (covered by `scripts/engine-tests.ts`); all I/O lives in `io.ts`; Runs execute in the background worker `jobs.ts` (Monitoring can cancel queued/running jobs and retry finished runs): `enqueueRun()` queues (one active job per pipeline), `processJobs()` claims jobs with leases and runs 5,000-row chunks, checkpointing after each (resumes across invocations, retries from the checkpoint, advances incremental watermarks in `pipelines.state` only after the whole run succeeds). Start a worker with `startWorker()` / `nudgeWorker()` (`lib/pipelines/worker.ts`, uses `after()`), never run a pipeline inline in a request. `runner.ts` keeps test runs, summaries and alerts. Timestamps without a zone are always treated as UTC. Postgres/MySQL reads pass column types from the driver (`ChunkRead.types`) so datasets keep numeric and date types; the Nexus pool returns DATE as `YYYY-MM-DD` text. Writes to customer databases only go to data sources added as destinations, never create or truncate their tables. Scheduling is Supabase pg_cron (`drizzle/0013_scheduler_retention.sql`, fires when a pipeline is due, a job waits or a retention check is due) calling `/api/cron/pipelines` with `CRON_SECRET`, which must match the Vault secret `nexus_cron_secret`.
- **Several sources (lanes)** (phase A of the lanes design; later phases add Aggregate/Deduplicate, Enrich / API calls, defined dataset schemas): every Source step starts a lane; with several, exactly one has `driver: true` (a single Source is the driver implicitly, so old pipelines stay valid). Lanes meet in a **Join** (edges into it carry `port: 'left' | 'right'`; left = driving rows, right = looked up) or a **Union** (`sourceColumn`, default `_source`). The plan is pure in `lib/pipelines/lanes.ts` (`planLanes` / `lanePlan`: driver, `streamed` sources, `joins` in staging order with the sources feeding their right side, `passNodes`, `isStagedStep`; definition validation calls it: each lane ends at the Destinations or at the right side of one Join, Join sides from different lanes, ≤ 10 sources). Join logic (key normalization, one row per match / first by a column, keep / drop / quarantine with check `joinNoMatch`, clash prefix) is pure in `lib/pipelines/join.ts`. `transformChunk` is **async**: rows enter at `opts.entry` (default the driver); a Join asks `ctx.joinPartners(join, normalizedKeys)` (the only I/O, injected) and rows reaching a right port come back in `ChunkOutput.toStage`. The worker (`jobs.ts`) runs phases: stage every Join's right side (`progress.stage['<join>:<source>']` offsets, `nexus_stage` tables from `lib/pipelines/stage.ts`, rows as JSON + indexed normalized key `_k`, exactly-once per part/chunk, ≤ `MAX_STAGED_ROWS` per Join), then stream `plan.streamed` one after another (`progress.streamIndex`); staging is dropped in `finishJob` and swept after 48 h by the cron tick (`pipeline_stage_tables` registry). Staged rows never count as `rowsRead` (`totals.stagedRows`). Watermarks are per Source (`pipelines.state.watermarks[nodeId]`, plus the driver's in the legacy `state.watermark`; `currentWatermarks` in `runner.ts`). Sample tests (`runEngine`) read a staged lane by the sample's keys when its key reaches the Join unchanged (`pushdownColumn`, `readRowsByKeys` in `io.ts`: SQL sources and files), else up to 5,000 rows. Replays that re-enter at or before a Join stage again first; rows held inside a staged lane are skipped (re-run instead). **Blocking steps** (phase B): Aggregate and Deduplicate keeping the last / most recent row need every row; `isBlocking` in `lanes.ts`. The run is `plan.passes` (one per Source and per blocking step, `planPasses` orders them by what each needs); rows reaching a blocking step come back in `toStage` and are staged with their group key (`stageKey` in `jobs.ts`); a finish pass (`transformChunk(…, { startNodeId, finish: true })`) answers whole groups read in key order (`stageKeys` / `stageGroups`) with the pure `lib/pipelines/aggregate.ts` and continues after the step. Deduplicate keeping the first row streams via `ctx.seen` (`dedupeSeenField`, persisted like Validate unique). Removed duplicates are flags (`duplicateRemoved*` checks). An Aggregate refuses incremental reads of its lanes. `replayBlocked` decides which held rows need a re-run instead of a replay. **API calls in a lane** (phase C): Enrich (`type: 'enrich'`, read only: per row, or batch with keys in a query parameter / POST body list matched back by `matchField`) and "Changes data" (`type: 'apicall'`: create, optional update, no DELETE) run through `ctx.api` (`lib/pipelines/api-runtime.ts`, server only); planning, answer mapping (`answerTree`, `mapAnswer`, lists as rows / first / json), cache keys and ledger decisions are pure in `lib/pipelines/api-calls.ts`; sending is `lib/connectors/rest/call.ts` (`sendRestCalls`, also the agent's `apiCall` op, 1.4.0+) via `sendApiCalls` in `io.ts`, which returns the answers received before a failure. Enrich answers are cached per step in `api_call_cache` (mapped values only, sealed with `encryptCredentials`; 404 / empty = not found for 1 h; purged by the cron tick, `clearStepCache`, and right to erasure). "Changes data" writes `api_call_ledger` (per pipeline, step, key hash: content hash + sealed answer) right after each successful call, sends `Idempotency-Key` = `idempotencyKey()`, skips known unchanged records and never sends anything in a sample test; `sendApiCallTest` sends one real call (confirmed, audited, recorded). Each step counts calls in `progress.apiCalls` against the data source's `config.maxCallsPerRun` (`DEFAULT_MAX_CALLS`, raised by admins with `setMaxCallsPerRun`). An `apicall` step makes a version destructive for publish approval (`destructiveWrites`). Never stage or read a lane in a request.
- **DB TLS:** `lib/db/index.ts` and `scripts/db-ssl.mjs` verify the server certificate against the bundled Supabase root CA (`lib/db/supabase-ca.ts`, or `DATABASE_CA_CERT`); only localhost connects without TLS. Postgres data sources choose verify / require / disable (+ CA); Supabase hosts are always verified.
- **Type errors fail the build.** Run `pnpm typecheck` before pushing.
